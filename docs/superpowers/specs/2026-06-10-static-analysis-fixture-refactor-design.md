# Static Analysis Fixture Refactor Design

Date: 2026-06-10

## Goal

Make static-analysis invariant tests easier to browse without weakening the current coverage. The existing family fixture tree under `src/tests/static_analysis_testdata/` should remain the primary way to understand focused expectations. Long inline PuzzleScript fixtures in Node test files should move into that tree when they are better read as test specimens than as harness code.

## Current Problem

The repository already has useful fixture families such as `object_tags/`, `rule_tags/`, `movement_action/`, `winflow/`, `program_flow/`, `rulegroup_flow/`, and `mergeability/`. These are easy to browse because each directory groups small source files by analysis family.

Some newer invariant and runtime-contract regressions were added inline in:

- `src/tests/ps_static_analysis_node.js`
- `src/tests/run_static_analysis_runtime_contracts_node_test.js`

Those tests are precise, but the specimens are harder to discover. Multi-family bugs are especially hard to read because their rule tags, object tags, winflow behavior, movement-action behavior, and runtime-contract evidence sit together in one large JavaScript file.

## Architecture

Use a fixture-first hybrid structure:

- Keep existing family directories as the executable source of truth for focused static-analysis expectations.
- Allow small PuzzleScript sources to be duplicated across families when a regression needs multiple analyses.
- Add a human-only regression index that links related duplicated fixture files.
- Add one new executable family, `runtime_contracts/`, for small runtime-contract fixtures currently embedded in Node tests.

Example layout for the recent property inferred overwrite regression:

```text
src/tests/static_analysis_testdata/
  object_tags/property-inferred-overwrite.txt
  object_tags/property-inferred-overwrite.json
  rule_tags/property-inferred-overwrite.txt
  rule_tags/property-inferred-overwrite.json
  winflow/property-inferred-overwrite.txt
  winflow/property-inferred-overwrite.json
  movement_action/property-inferred-overwrite-action.txt
  movement_action/property-inferred-overwrite-action.json
  runtime_contracts/property-inferred-overwrite.txt
  runtime_contracts/property-inferred-overwrite.json
  regressions.md
```

The `regressions.md` file is for humans only. It should explain which fixture stems belong to the same bug story, but the test runner should not read it. This avoids introducing a second cross-family schema.

## Existing Family Fixtures

Existing families should continue to use `static_analysis_testdata_runner.js`:

1. A `.txt` file contains a complete PuzzleScript source.
2. A matching `.json` file contains only the curated expectations for that family.
3. Missing `.json` files can be generated by `make static_analysis_tests`.
4. Generated JSON remains a proposal and must be reviewed before committing.

Moving inline tests into existing families should be mechanical:

1. Copy the PuzzleScript source into the relevant family directory.
2. Run `make static_analysis_tests`.
3. Trim the generated JSON to the intended assertions.
4. Remove the corresponding inline assertions only after the family fixture covers the behavior.

Duplicating a small source across family folders is acceptable. The priority is local readability inside each family directory.

## Runtime Contract Fixtures

Add `src/tests/static_analysis_testdata/runtime_contracts/` for focused runtime contract specimens. Each fixture should have:

- A `.txt` complete PuzzleScript source.
- A `.json` file with replay inputs, expected final serialized level, and selected summary expectations from `runSimulationWithStaticChecks()`.

Suggested JSON shape:

```json
{
  "schema": "ps-static-analysis-testdata-v1",
  "inputs": ["tick"],
  "expectedFinalLevel": "background player:0,background obja:1,\n",
  "expect": {
    "neverAppearsObjectCount": 0
  }
}
```

The runner should compare only listed `expect` fields. It should also generate missing JSON from observed results, following the existing review-before-commit policy.

Document the `runtime_contracts` fields in `src/tests/static_analysis_claim_descriptions.json` so undocumented fields continue to fail loudly.

## Human Regression Index

Add `src/tests/static_analysis_testdata/regressions.md`.

Each entry should be short:

- Regression name.
- One or two sentences describing the bug shape.
- A list of family fixture files that cover it.

Example:

```markdown
## Property Inferred Overwrite

`[ Thing ] -> [ Thing ObjA ]` must not treat `Thing` as preserved on the
`ObjA, ObjB` layer, because `ObjA` can overwrite an initial `ObjB`.

- `rule_tags/property-inferred-overwrite.*`
- `object_tags/property-inferred-overwrite.*`
- `winflow/property-inferred-overwrite.*`
- `movement_action/property-inferred-overwrite-action.*`
- `runtime_contracts/property-inferred-overwrite.*`
```

This index is not a manifest. It should not affect test execution.

## Scope For First Implementation

The first implementation should stay small:

1. Add `runtime_contracts/` runner support.
2. Add README and claim-description documentation for `runtime_contracts`.
3. Add `regressions.md`.
4. Move the recent property inferred overwrite regression into family fixtures.
5. Optionally move a nearby small cluster of inline count/static/property overwrite fixtures if they fit cleanly.

Do not attempt to drain all of `ps_static_analysis_node.js` in the first pass.

## Non-Goals

- Do not change static-analysis behavior.
- Do not create a cross-family executable manifest.
- Do not deduplicate fixture source by reference in the first pass.
- Do not move broad solver-corpus assertions or harness meta-tests into fixture files.

## Testing

Implementation should verify:

```sh
make static_analysis_tests
node src/tests/ps_static_analysis_node.js
node src/tests/run_static_analysis_runtime_contracts_node_test.js
node src/tests/run_static_analysis_runtime_contracts_node.js --filter "super tricky"
git diff --check
```

If the branch also contains canonicalizer changes, also run:

```sh
node src/tests/canonicalizer_node.js
```

Full `node src/tests/run_tests_node.js` can be run as an additional broad check, but current known unrelated failures should be reported separately rather than treated as part of this refactor.

## Success Criteria

- Future static-analysis regressions can be found by browsing `static_analysis_testdata/`.
- Multi-family bugs have an obvious human index entry.
- Each family remains independently understandable.
- Runtime contract specimens are no longer hidden inside a long Node harness file.
- Runner changes are small and schema-checked.
- Existing test behavior is preserved.
