## The Voitex regression

Game: `Voitex Rasteriser 2 [2nd Demake of Vertex Dispenser Puzzle Mode]`, testdata.js line 1121.

The pattern that breaks:
```
right [ action num temp | ] -> [ action num temp | > num ]
```
where `num = 1 or 2 or 3 or 4 or 5 or 6 or 7 or 8 or 9` (each on its own collision layer).

With 5c-3 active, this rule is coalesced into one with two RHS positions in `propertySinks`:
- Cell 0 (`action num temp`): same-cell preserve with `action` direction. The compiler routes this through `inferredPropertyBindings` (dirMode=2, dirMask=16=action bit). The legacy `layerCoupledMovementReplacements` path is skipped because `propertyInferredSink=true`.
- Cell 1 (`> num`): cross-cell sink with `right` direction (after `>` normalization). Also routed through `inferredPropertyBindings` (dirMode=2, dirMask=8=right bit).

At runtime, the levels' end state diverges from the recorded testdata. Voitex's main game-loop is creating numbered objects in a cascading sequence (`[action player no N] -> [player action N pN fixed temp]` for N=1..9, then cascading via the `> num` rule), and only the low numbers (1, 2, occasionally 3) appear in the actual output where the expected has 1..9 + p1..p9.

## What I tried and what didn't work

- **Hypothesis 1**: same-cell preserves with non-empty direction should fall through to the legacy `layerCoupledMovementReplacements` path. I added a check in `rulesToMask`'s sink-detection to compare `(rowIndex, colIndex)` against `rule.propertyBindingsArr`'s `sourceRow`/`sourceCell` and skip `propertyInferredSink=true` when they match. **Didn't fix Voitex.** So cell 0 routing is not the (only) bug.

- **Hypothesis 2 (untested)**: cross-cell sink cell 1's runtime apply is wrong. The engine code at engine.js:2090-2105 does `movementsClear.ishiftor(0x1f, 5 * captured.layerIndex)` then `movementsSet.ishiftor(b.dirMask, 5 * captured.layerIndex)`. Maybe the captured layer is wrong, or `b.dirMask` is wrong relative to the rule's scan direction, or there's an ordering issue with how `inferredPropertyBindings`-driven writes compose with the cell's static `replacement.movementsSet`/`movementsClear`/`movementsLayerMask`.

- **Hypothesis 3 (untested)**: `>` direction normalization in `convertRelativeDirsToAbsolute` + `rewriteUpLeftRules` doesn't propagate cleanly into the 5c-3 `dirMask` field. For `up`/`left` rules that get rewritten to `down`/`right` with cell-order reversal, the recorded `dirMask` might not match the post-rewrite scan direction.
